You want a small, idiomatic sw-MLPL demo that captures the useful Jev idea without pretending to reproduce Jev’s unpublished internals: unstructured state in, bounded typed decisions out, probabilities visible, code owns the branch. Given what you already have in demo-decision-model, moe-microscope, and microgpt-mlpl, I think this can be much smaller and sharper than another standalone framework.

The key observation

The HN-linked “Jev in 25 lines of Python” is essentially:

prompt
  -> ordinary small causal LM
  -> take logits at one position
  -> select logits for A/B/C
  -> softmax only those logits
  -> probabilities over bounded choices

The example uses Qwen3-0.6B and gets:

Legitimate  .031
Spam        .084
Phishing    .885

without generating a token at all.

That is an excellent teaching demo, but it leaves out the important Jev distinction: TypeSafe says Jev is specifically trained/post-trained for calibrated decisions, parallel typed outputs, and non-generative operation. Its RLCD training procedure and architecture are not public.

Your demo-decision-model already makes this distinction correctly: it explicitly says it reproduces the contract and calibration objective, not Jev's unpublished architecture. More importantly, it already demonstrates the deeper idea better than the 25-line Python example: code owns thresholds, strings, memory, and side effects, while the model supplies bounded probabilistic judgments.

So I would not build another large Jev-inspired project.

I would add a tiny MLPL artifact whose purpose is:

Show that “typed decision” is just a natural MLPL computation.

Proposed demo: jev-like.mlpl

I would aim for ~20–35 substantive MLPL lines.

The conceptual pipeline should be just:

state
  ↓
features / embedding
  ↓
decision head
  ↓
logits
  ↓
softmax
  ↓
typed result

No token sampling. No generation loop. No decoder. No agent.

The demo should start with Choice, because it exposes the idea most clearly.

Something structurally like this:

choices = ["legitimate", "spam", "phishing"]

x = encode("Payroll asks for your password on a non-company sign-in page.")

logits = x @ W + b
p = softmax(logits)

decision = choices[argmax(p)]

print(decision)
print(p)

The exact syntax obviously needs to match current MLPL facilities, but that is the level of abstraction I would target.

The important point is that in MLPL this should look like the mathematics rather than framework plumbing.

Conceptually:

$$ z = xW+b $$ $$ p_i = \frac{e^{z_i}}{\sum_j e^{z_j}} $$ $$ choice=\operatorname{argmax}(p) $$

That is the entire inference mechanism for a fixed-head decision model.

And unlike the HN example, you're not abusing next-token probabilities from a chat model.

But make it actually Jev-like: three heads, one state

The smallest compelling version should probably be slightly more ambitious.

Jev exposes three useful shapes:

Choice — distribution over alternatives
Noul — probability of yes/no
Score — ordered rating

TypeSafe emphasizes that multiple questions are evaluated from the same input state rather than autoregressively generating answers.

Your demo-decision-model already has exactly the right architecture for this idea: one pooled representation feeding a Choice head and several Noul heads.

So the killer MLPL demonstration would be:

                       +--> Choice: category
                       |
text -> encoder -> h --+--> Noul: suspicious?
                       |
                       +--> Scale: urgency

Conceptually:

h = encode(state)

category = softmax(h @ W_category + b_category)
suspicious = sigmoid(h @ w_suspicious + b_suspicious)
urgency = softmax(h @ W_urgency + b_urgency)

Then ordinary code interprets them.

category:
  legitimate  .02
  spam        .07
  phishing    .91

suspicious:
  true        .97

urgency:
  low         .01
  medium      .13
  high        .86

That is much closer to the actual System-One programming model than the HN article while still being tiny.

Why MLPL is unusually well suited to this

This is where I think the demonstration becomes valuable for sw-MLPL itself.

The HN implementation needs Python + NumPy + llama.cpp + GGUF + tokenizer handling + token IDs because it starts from an autoregressive LM.

MLPL can express a purpose-built decision model directly.

Your language already has native:

arrays
broadcasting
matmul
softmax
cross_entropy
autograd
Adam
Model DSL
WASM execution
MLX/CUDA backends

And microgpt-mlpl demonstrates why that matters: its idiomatic version shrinks an entire GPT to 48 lines, because MLPL's array operations and Model DSL eliminate the scalar/autograd machinery. In your measured result that version is also faster than the scalar Rust implementation.

The same effect should be even stronger here.

A decision model is a much more natural array-language workload than GPT.

I would build the demonstration in four increasingly-real versions

Not four large programs—four tiny stages in one literate demo.

1. Pure math: no learned model

Start with logits directly:

logits = [1.2, 2.0, 4.1]
p = softmax(logits)

Output:

legitimate  0.046
spam        0.102
phishing    0.852

Purpose:

A typed decision is a probability distribution over a finite domain.

Maybe 5–8 lines.

2. Learned Choice

Then:

features -> linear -> softmax

Train on a tiny corpus.

model = linear(features, 3, seed)

repeat 200 {
    logits = model(X)
    loss = cross_entropy(logits, y)
    adam(...)
}

Now the probabilities came from training rather than being invented.

That distinction is important.

3. Shared representation + typed heads

Then make the MLPL idiom explicit:

h = encoder(X)

route    = softmax(h @ Wr + br)
question = sigmoid(h @ Wq + bq)
risk     = softmax(h @ Ws + bs)

One computation of h.

Three decisions.

This is the point where the diagram becomes:

                 ┌─ route ─────── Choice
state → encoder ─┼─ question? ─── Noul
                 └─ risk ──────── Scale

This directly connects to what you've already implemented in demo-decision-model.

4. Calibration experiment

This is the stage the 25-line Python demo cannot honestly claim.

Take a held-out set and bucket predictions:

confidence    predicted correct
0.5–0.6       54%
0.6–0.7       63%
0.7–0.8       74%
0.8–0.9       81%
0.9–1.0       92%

Then show an ECE/Brier score before and after temperature scaling.

Something like:

p_raw = softmax(logits)
p_cal = softmax(logits / temperature)

This is pedagogically powerful because:

classification ≠ calibration

and HN commenters immediately identified exactly that issue. Several specifically point out that extracting normalized choice logits does not automatically make those numbers calibrated probabilities.

Your current demo-decision-model has already observed the problem empirically: early models can be highly confident while wrong off-distribution.

That gives you actual evidence rather than marketing.

The compact MLPL version I would strive for

Ignoring data loading and reporting, I think the essential learned model should read approximately like this:

# state representation
h = mean(embedding(tokens, vocab, dim), 0)

# typed heads
choice_p = softmax(h @ choice_W + choice_b)
question_p = sigmoid(h @ question_W + question_b)
risk_p = softmax(h @ risk_W + risk_b)

# typed answers
choice = choices[argmax(choice_p)]
question = question_p >= 0.5
risk = sum(risk_p * [1, 2, 3])

print(choice)
print(choice_p)
print(question_p)
print(risk)

Even better if the Model DSL lets this collapse further.

The MLPL teaching point becomes:

There is no decoding loop because there is nothing to decode.

That is the line I would put prominently in the demo.

Do not use A/B/C internally if you can avoid it

One interesting point from the HN discussion is that using next-token labels such as A, B, C introduces tokenization and positional biases. One commenter reports needing permutations of A/B assignments and checking that the allowed-token probability mass dominates the distribution.

That's another reason your MLPL version can be cleaner.

Instead of:

token A → phishing
token B → spam
token C → legitimate

your head literally means:

column 0 → legitimate
column 1 → spam
column 2 → phishing

There is no tokenizer-level ambiguity.

That is a genuine advantage of the dedicated decision model.

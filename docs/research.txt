Yes. ELIZA is unusually well suited as a Jev/System-One demonstration, because it cleanly separates understanding/decision-making from text generation.

The key is not to build a better chatbot. Build a modern implementation of the original ELIZA idea in which all words spoken by ELIZA remain deterministic, canned text, while a learned model replaces the pattern-matching machinery that decides which canned response/rule to invoke.

TypeSafe describes Jev as “unstructured state in, typed probabilistic decisions out,” with predefined outputs, probabilities/confidence, and no generated strings. Their workflow examples explicitly decompose applications into narrow model judgments plus conventional program logic.

1. Why ELIZA makes a good demonstration

Classic ELIZA already has roughly the architecture we want:

text
  ↓
pattern recognition
  ↓
rule selection
  ↓
transform / substitution
  ↓
canned response

A Jev-inspired version becomes:

text
  ↓
learned classification
  ↓
typed probabilistic decision
  ↓
ordinary program logic
  ↓
canned response

This demonstrates an important distinction much better than another customer-service classifier would.

Generative LLM
"My mother hates my job."
       │
       ▼
     LLM
       │
       ▼
"What makes you think your mother
disapproves of your career?"

Everything after the input is potentially generated.

Jeviza
"My mother hates my job."
       │

       │

The intelligence is being used as a fuzzy branch instruction, which is almost exactly TypeSafe's “smart if-statement” framing.

And the demo has a wonderful property:

The model literally cannot invent an ELIZA response.

It can choose the wrong response, but it cannot generate a response outside the table.

That is a much more precise demonstration of the “no hallucination” claim than simply saying the output is JSON. TypeSafe's claim should be interpreted this way too: schema conformance doesn't mean the decision is factually correct; it means the model cannot invent an output outside the permitted space.

2. Don't try to clone Jev itself

There is an important limitation.

TypeSafe has disclosed the behavioral architecture, but not enough information to reproduce Jev's actual neural architecture. They say it involves a new model architecture, parallel sampler, and RLCD training, but haven't published weights or implementation details.

So I would explicitly describe the project as:

An open experimental implementation of System-One-style decision models inspired by the publicly described Jev interface.

That gives us something scientifically useful rather than pretending we reverse-engineered Jev.

I'd separate the research into three levels:

Level	Goal
0	reproduce the interface semantics
1	build a tiny non-generative decision model
2	investigate calibration/training similar in spirit to RLCD

The ELIZA demo exercises all three.

3. Start with three primitives

TypeSafe's workflow evals expose three useful abstractions: Noul, Choice, and Score. Noul produces a probability for yes/no; Choice returns a distribution over predefined choices; Score produces a rating/distribution over an ordered scale.

I'd implement our own generic Rust interface:

pub trait SystemOne {
    fn choice(
        &self,
        state: &State,
        choices: &[Choice],
    ) -> ChoiceResult;

    fn score(
        &self,
        state: &State,
        levels: &[Level],
    ) -> ScoreResult;

    fn noul(
        &self,
        state: &State,
        proposition: &str,
    ) -> Probability;
}

Conceptually:

struct ChoiceResult {
    selected: ChoiceId,
    probabilities: Vec<f32>,
    confidence: f32,
}

Notice what is not present:

generate(prompt) -> String

That's fundamental.

8. Calibration is where the experiment becomes research

Simply applying softmax doesn't give us what TypeSafe claims.

A neural classifier might say:

MOTHER = .93

while being correct only 72% of the time when it reports ~.93.

That's not calibrated.

We therefore want to measure:

predicted confidence     actual accuracy

0.50–0.60                 0.56
0.60–0.70                 0.64
0.70–0.80                 0.76
0.80–0.90                 0.85
0.90–1.00                 0.94

That gives us an opportunity to implement and compare:

raw softmax
temperature scaling
Platt scaling
isotonic calibration
Brier-score optimization
ECE calibration

And later an experimental RLCD-inspired training stage.

I would not initially claim that this reproduces TypeSafe's RLCD; they have not published enough detail for that. Their public claim is that RLCD optimizes for calibrated decisions.

But we can independently ask:

Can training directly against proper scoring rules produce better calibrated decision probabilities?

That's a legitimate experiment.

Rather than expecting the first pass to solve everything, let the application dynamically formulate another typed question.

64-dimensional h

Then stop.

There is no vocabulary projection and no next-token prediction.

Instead, h feeds decision heads.

For example:

$$ P(action|x)=softmax(W_a h+b_a) $$ $$ P(topic|x)=softmax(W_t h+b_t) $$ $$ P(recall|x)=sigmoid(w_r^T h+b_r) $$

So one forward pass might produce:

ACTION
  reflect       .09
  ask           .14
  recall        .71
  fallback      .06

TOPIC
  family        .61
  work          .17
  feelings      .14
  other         .08

RECALL?
  true          .83

That parallels TypeSafe's description of answering many decomposed questions from the same state in parallel.

2. The interesting part is that the questions should be inputs

There's an important problem with the architecture above.

If we hard-code:

action_head
topic_head
recall_head

we've built a specialized ELIZA classifier.

Jev appears more general than that. Its interface accepts a state and structured questions, with the legal answers defined by the query. TypeSafe explicitly describes possible outputs as defined in advance for a query and says their demos submit multiple questions against shared state.

So a closer PoC would encode both state and question:

                    ┌─────────────┐
conversation ──────►│ state       │──► h
                    │ encoder     │
                    └─────────────┘
                           │
                           │
question ──────────────────┼──► scorer
                           │
candidate A ───────────────┤
candidate B ───────────────┤
candidate C ───────────────┤
                           ▼
                      probabilities

Conceptually:

$$ s_i = f(h_{state}, h_{question}, h_{choice_i}) $$

then

$$ P(choice_i)=softmax(s_i) $$

That's significantly more Jev-like.

3. Train on (state, question, choices, answer)

Instead of an ELIZA dataset like:

"My mother hates me" → FAMILY_RESPONSE

make the training representation general:

STATE:
    "My mother hates me."

QUESTION:
    "What should ELIZA do next?"

CHOICES:
    REFLECT
    FAMILY
    ASK
    RECALL
    FALLBACK

TARGET:
    FAMILY

    "What is the primary topic?"

    FAMILY

    SELF
    POSSESSION
    OTHER

TARGET:
    FAMILY

and:

QUESTION:
    "Would recalling an earlier statement help?"

CHOICES:
    YES
    NO

TARGET:
    NO

Now we've stopped training a conventional single-purpose classifier.

We're training a conditional decision model:

$$ P(y\mid state, question, choices) $$

That's the abstraction I would build.

4. Candidate choices should also be semantic inputs

This becomes particularly important for your earlier-memory example.

Don't make the model have outputs:

MEMORY_0
MEMORY_1
MEMORY_2
...

Instead score arbitrary candidates.

Suppose ordinary code retrieves:

A: "My mother worries about me."
B: "My job has been stressful."
C: "I bought a car."
D: NONE

The model receives approximately:

STATE:
    current conversation state

QUESTION:
    Which previous statement would be
    most useful to recall now?

CHOICES:
    A "My mother worries about me."
    B "My job has been stressful."
    C "I bought a car."
    D NONE

The model scores each:

$$ score_i = f(state, question, candidate_i) $$

giving:

A    .13
B    .68
C    .04
NONE .15

This is much more powerful than a fixed classification head because the classes did not exist during training.

That's an important property I'd try to achieve.

5. That suggests a dual/cross-encoder architecture

For our tiny model, I'd experiment with two designs.

A. Cross encoder — more capable

Encode everything together:

[state]
[question]
[candidate]
      │
      ▼
 tiny encoder
      │
      ▼
    score

Run once per candidate.

Good accuracy, but duplicated computation.

B. Shared state encoder — more Jev-like computationally
                 STATE
                   │
                   ▼
             state encoder
                   │
                   h
       ┌───────────┼───────────┐
       │           │           │
       ▼           ▼           ▼
   question A  question B  question C
       │           │           │
       ▼           ▼           ▼
    choices      choices      choices
       │           │           │
       ▼           ▼           ▼
    scores       scores       scores

Compute expensive state representation once.

Then the decision scorer is cheap:

$$ score(h,q,c) $$

That fits TypeSafe's claim that many independent questions can be answered in parallel against the same state. We don't know whether Jev literally does this, but it's a reasonable architectural inference from the published behavior.

6. Training starts as supervised learning

I would not start by trying to invent RLCD.

First train with ordinary cross entropy:

$$ L_{choice}=-\log P(y) $$

For binary questions:

$$ L_{binary}=BCE(y,p) $$

For several questions from the same state:

$$ L=\sum_q L_q $$

This establishes whether the architecture can learn the task at all.

For ELIZA, generating thousands of examples is easy because the original rules can become a teacher.

For example:

ELIZA rule engine
       │
       │ generate/paraphrase inputs
       ▼
"My mom is always..."
       │
       ▼
classic rule engine
       │
       ▼
FAMILY_RESPONSE

Thus the original symbolic ELIZA becomes the ground-truth oracle.

That's pedagogically delightful:

1966 symbolic program
        │
        │ teacher
        ▼
2026 tiny neural decision model
7. Then calibration becomes the critical experiment

Ordinary classification training optimizes:

Was the correct answer ranked highest?

But Jev's major claim is stronger:

Does .80 actually mean approximately an 80% chance of correctness?

TypeSafe calls its method Reinforcement Learning for Calibrated Decisions (RLCD) and emphasizes epistemically honest probabilities. They haven't publicly described enough of the algorithm for us to reproduce it.

But we can reproduce the objective.

Suppose the model says .8 on 100 held-out examples.

Approximately 80 should be correct.

So measure:

Brier score
$$ BS=\frac{1}{N}\sum(p-y)^2 $$
Negative log likelihood
$$ NLL=-\frac1N\sum \log P(y) $$
Expected Calibration Error

Bucket predictions:

confidence     actual accuracy

.50-.60          .54
.60-.70          .63
.70-.80          .76
.80-.90          .83
.90-1.0          .94

And draw a reliability plot:

accuracy
1.0 |                         *
 .8 |                   *
 .6 |             *
 .4 |
 .2 |
    +---------------------------
       .2 .4 .6 .8 1.0
             confidence

       ideal = diagonal

This belongs naturally in your microscope.

8. Then invent our own "RLCD-like" second training phase

Once supervised learning works, then we can experimentally optimize calibration.

I wouldn't call ours RLCD because we don't know their algorithm.

Call it something like calibration fine-tuning.

A simple objective could combine classification and calibration:

$$ L = L_{CE} +\lambda L_{Brier} $$

Or use a proper scoring rule directly.

Then compare:

                   accuracy    ECE     Brier

cross entropy        .91       .14      .10
+ temperature        .91       .05      .08
+ Brier training     .90       .03      .07

Temperature scaling is particularly useful as a baseline because it can improve calibration without retraining the encoder.

Then we'd know whether the exotic training technique is even necessary at our tiny scale.

There's one especially revealing detail in TypeSafe's post.

They say Jev supports choice cardinality up to 255, and for higher-cardinality cases they use a two-stage system: independently score candidates, then make an explicit choice.

That is remarkably close to what we independently proposed for ELIZA memory retrieval.

For 100 previous statements:

                100 memories

                     ▼

Distilling ELIZA from a GPT teacher

I think your proposed pipeline is exactly the right experiment, with one modification:

Don't ask the GPT teacher to generate ELIZA responses. Ask it to make ELIZA decisions.

That's a major distinction.

The teacher's job becomes:

conversation
     │
     ▼
large local GPT teacher
     │
     ▼
structured decisions

For example:

{
  "action": "RECALL",
  "topic": "FAMILY",
  "response_style": "QUESTION",
  "recall_turn": 3,
  "confidence": 0.91
}

The student learns those decisions.

The application still owns the canned ELIZA text.

1. Define the decision vocabulary first

I'd start with perhaps 8–12 actions, not dozens.

Something like:

Action	Meaning
GREET	greeting response
YES	response to affirmation
NO	response to negation
DONT_KNOW	uncertainty response
REFLECT	reflect current statement
ASK_MORE	ask user to elaborate
RECALL	mention earlier statement
TOPIC_SHIFT	move conversation elsewhere
KEYWORD	classic ELIZA keyword response
FALLBACK	generic canned response

Then separate dimensions:

ACTION:
    RECALL

TOPIC:
    FAMILY

TONE:
    NEUTRAL

QUESTION:
    true

MEMORY_REQUIRED:
    true

Don't create:

RECALL_FAMILY_NEUTRAL_QUESTION

as one giant class.

That causes combinatorial explosion.

Instead we want factorized decisions.

2. Make the GPT teacher play ELIZA

Give the local GPT a fairly strict system prompt describing classic ELIZA behavior.

Then generate conversations.

For example:

USER:
My mother calls me too often.

TEACHER:
{
  action: KEYWORD,
  topic: FAMILY,
  recall: false
}

Later:

I don't know.

{
  action: RECALL,
  topic: FAMILY,
  recall: true
}

1: "I went shopping yesterday."
2: "The weather has been nice."
NONE

Teacher:

0

Now we've generated a supervised training example.

3. But don't use only GPT-generated conversations

This is where I think we can make the project substantially stronger.

Use three sources of training data:

                   training corpus

       ┌───────────────┼────────────────┐
       │               │                │
       ▼               ▼                ▼

     rules          + mutation      conversations

                 train student

Generate variations:

My mother likes me.

My mom keeps calling.
Mom doesn't understand me.

These can cheaply produce enormous datasets.

C. GPT-generated paraphrases and difficult examples

This is where the expensive teacher earns its keep.

Ask it for things like:

You might get:

The woman who raised me never understood me.
She was always critical when I was growing up.
Growing up, I could never please her.
...

Now the student has to learn semantics rather than keywords.

4. Teacher-generated data should deliberately attack the rules

This is important.

Don't have the GPT simply produce random ELIZA conversations.

Have it generate curriculum categories.

For example:

easy
    explicit keyword

paraphrase
    semantic equivalent without keyword

ambiguous
    two plausible actions

negative
    keyword present but wrong interpretation

memory
    appropriate earlier statement

memory-negative
    no earlier statement worth recalling

topic-shift
    conversation has become repetitive

short-input
    yes / no / maybe / dunno

adversarial
    misleading keyword overlap

Then we know what the student is learning.

5. The GPT teacher should output distributions, too

Instead of:

ACTION = RECALL

ask:

RECALL       .70
ASK_MORE     .20
REFLECT      .07
TOPIC_SHIFT  .03

Now we're doing soft-label distillation.

This is much better than throwing away the teacher's uncertainty.

The student minimizes something like:

$$ L_{KD}=KL(P_{teacher}\Vert P_{student}) $$

instead of merely:

$$ L_{CE}=-\log P_{student}(y) $$

So if the teacher thinks:

RECALL       .51
ASK_MORE     .45

we don't lie to the student and tell it:

RECALL = absolute truth

That is especially relevant to the Jev-inspired calibration objective.

6. But don't trust GPT confidence

This distinction is critical.

A GPT saying:

confidence = .93

does not mean the event has a calibrated 93% probability.

TypeSafe explicitly identifies overconfidence and inconsistent confidence as a weakness of conventional LLMs and makes calibrated probability part of its alternative design.

So I'd distinguish:

Teacher distribution

Useful training signal:

RECALL      .55
ASK_MORE    .40
OTHER       .05

from:

Ground-truth calibration

Measured empirically against held-out examples.

We should never assume the former provides the latter.

16. And this is probably where our "Jev-like" training differs from ordinary distillation

The objective isn't:

Make tiny model imitate big model.

It's:

That gives us a multi-objective optimization:

$$ \text{minimize} \quad \begin{cases} \text{classification error}\\ \text{calibration error}\\ \text{parameters}\\ \text{latency}\\ \text{active bytes}\\ \text{energy} \end{cases} $$

That's almost tailor-made for moe-microscope.

Eventually teacher usage should fall dramatically because the tiny model already handles the easy decision surface.

And unlike normal LLM distillation, we don't care whether the student can speak English. It only needs to learn a few very specific decision boundaries.

That's why I think the parameter count could become surprisingly small—and why ELIZA is a particularly strong first experiment. It gives us a deterministic reference implementation, essentially unlimited synthetic examples, GPT-generated linguistic diversity, objectively measurable decisions, memory/tool-like branching, and canned output that prevents generative ability from hiding failures.

The natural end goal is not "tiny ELIZA." It's demonstrating a general GPT → distilled Typed Decision Model pipeline where a large generative model is used offline as a teacher, while the deployed system is a tiny, fast, non-generative probabilistic decision engine. That generalizes directly from ELIZA to the campus docent/navigation problem and eventually to decision points inside agents and workflows.
